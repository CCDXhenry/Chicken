# 开发、验证与交付

提取自通用工程的源码探索、严格检查、Studio、包同步及 Git 约定。

## 探索与类型检查

- 优先使用文本搜索与路径过滤定位当前源码及调用方。动态 require 路径、实例树和运行期状态须结合源码与 Studio 只读查询确认。
- **脚本首行中文注释与 strict 规范**：所有新增业务脚本必须在第一行添加脚本作用的中文注释，准确描述模块职责与调用定位。第二行保留 `--!strict`（明确的外部第三方依赖和生成数据除外）。修改既有脚本时，首行若无中文注释应一并补齐。
- 类型错误通过准确类型、nil 分支及 IsA 收窄修复，不删除 strict、不扩大为 any、不用无意义 assert 掩盖错误。无返回值标注使用 `: ()`。
- **统一严格类型分析与门禁（参考 TheGreatEscape）**：
  - 单文件/多文件即时分析：`pwsh -File Tools/check-strict.ps1 <脚本路径>`
  - Git 提交前暂存区门禁：`pwsh -File Tools/check-strict.ps1 -Staged`
  - 全仓库全量检测：`pwsh -File Tools/check-strict.ps1 -All`
  - 核心分析器基于 `luau-lsp analyze`，配合 `Tools/globalTypes.d.luau` 及脚本动态构建的 DataModel `sourcemap.json`，自动隔离未修改依赖的既有警告。

## Studio 与源码同步

- 本地文件为代码编辑入口，沿用 Script Sync 机制；不通过 MCP 直接覆写 Studio 源码，不提交未经验证的草稿。
- 在 **Edit 模式** 下创建或修改持久化 UI、模型和属性。Play 中的临时改动不能当成已保存的场景资产。
- 在 Edit 模式下不要 `require` 业务模块来证明逻辑通过；实际逻辑验证使用已获授权的 Play 会话。核对源码内容不需要启动 Play。
- 报告实际检查方式及其限制：源码一致、静态类型无错和实际运行成功是不同维度的结论。

## 共享代码与 Package

- 辨别基础共享代码与当前业务代码，不将具体业务逻辑强行混入基础公用库中。
- Script Sync、Git 提交均不表示 Package 已发布。不自动升级包或向其他项目随意复制代码。
- 纯文档或 skill 改动，明确说明无需包同步。

## Git 与文档

- SVN 元数据及公共 External 保持原状；Git 忽略规则必须继续覆盖嵌套 `.svn`，同时保留工具运行依赖。
- 可在任务内检查 status/diff/log；提交、推送和创建 PR 各自要求用户授权，不把一个动作的授权延伸到另一个。已有明确授权在相应范围内继续有效。
- 提交前检查范围、验证结果及敏感配置。
- 用户要求导出实现方案或设计 Markdown 时，保存到根目录 `功能文档/`，使用中文业务文件名；不为普通回复或小改动额外生成方案文件。
