# 编码规范

## 语言与基础规则

- 默认使用 Roblox Luau 编写代码，遵循官方 API 与最佳实践。
- 本项目业务脚本必须在第一行声明 `--!strict`。
- `Scripts/ReplicatedStorage/GameAnalytics/` 及明确标注的第三方 / vendor 目录不强制 `--!strict`，勿为规范而修改上游代码。
- `GameConfig` 目录下除 `init` 外为插件生成文件，严禁修改。
- 除了 `ModuleScript` 外，其余 `LocalScript` / `Script` 禁止包含模块定义代码或导出接口。

## 命名规范

- 所有命名必须使用有明确语义的英文单词或通用缩写。
- 变量命名使用 `lowerCamelCase`。
- 常量命名使用 `UpperCamelCase`。
- 函数命名使用 `UpperCamelCase`。
- 函数命名语义采用「动词 + 描述」。
- 回调函数必须以 `On` 开头。
- 类型命名使用 `UpperCamelCase`。

## 常量定义

- 禁止直接使用魔法数字。所有有意义的数值、颜色、时间周期、资源 ID 等必须定义为常量或配置。
- 多处共用的配置、静态数据或资源 ID 放入 GameConfig。

## 后缀约定

- 数据层脚本：`Info`。
- 界面层脚本：`Frame`。
- 管理器脚本：`Manager`。
- 工具脚本：`Tool`。
- 静态数据变量或类型：`Data`。
- 动态运行期变量或类型：`Info`。
- 列表：`List`。
- 映射：`Map`。
- UI 元素后缀必须对应 Roblox GUI 类型，如 `Frame` / `Text` / `Image` / `Button`。

## 单文件脚本顺序

`LocalScript` / `Script` / `ModuleScript` 自上而下必须按以下顺序组织，禁止随意打乱：

1. 获取各 Service，如 `game:GetService(...)`。
2. `require` 各 `ModuleScript`，模块引用集中写在文件前部。
3. 获取 `ReplicatedStorage` 下各原始对象，如 Folder、模板等实例引用。
4. 类型定义：`type`、`export type`。
5. 常量定义：脚本级常量。
6. 变量定义：模块级 / 脚本级变量，包含表与状态。
7. 函数定义：局部函数与模块函数。
8. 事件监听：`Connect` / `:On()` 等绑定，放在初始化完成之后。
9. 逻辑初始化代码：一次性初始化调用与启动逻辑。

## 函数与代码组织

- 函数职责必须单一，禁止在单一函数中堆叠多个独立逻辑。
- 复杂逻辑必须拆分为多个子函数。
- 脚本中的函数按以下顺序组织：
  1. 更新函数：`Update` / `Tick` / `Refresh` 等周期性或状态刷新相关函数。
  2. 初始化函数：`Init` / `Setup` / `Initialize` 等一次性初始化逻辑。
  3. 事件监听与回调函数：`OnXXX` 形式的事件处理函数。
- 禁止在脚本中随意打乱函数定义顺序。
- 所有可能为空的对象访问前必须进行非空判断；Roblox Studio 中已预先添加的对象不用判空。
- 关键异常场景必须输出错误日志或提示。
- 最外层脚本不要使用内联匿名 `function`，应使用具名局部函数或模块级函数。
- 所有服务、模块的 `require` 必须写在文件顶部，禁止在函数内动态调用。

## 脚本同步方式

本项目使用 Script Sync 进行本地文件与 Roblox Studio 的双向同步，未使用 Rojo。保持文件系统与 Studio 层级一致。修改代码统一修改本地文件代码，即会自动同步到 Roblox Studio，禁止使用 MCP 直接修改 Roblox Studio 代码，禁止在 Roblox Studio 提交草稿。

## 架构分层

使用数据层、逻辑层、表现层三层分离架构：

- 数据层只提供简单的数据获取与数据更新接口，数据变化时发送消息。
- 服务端以 `ServerGameInfo` 为唯一真相源，客户端通过 `ClientGameInfo` 映射。
- 逻辑层只负责业务逻辑与数据修改。
- 服务端 `XXXManager` 负责校验与计算，客户端 `XXXManager` 响应输入。
- 各系统主入口必须暴露 `.Init()`，由总控统一调度，禁止业务内自行 `task.spawn` 野蛮启动。
- 表现层只负责表现部分，不直接修改数据。
- 表现层只能通过数据层获取数据。
- 表现层监听数据变化消息更新表现，不与逻辑层强耦合。

## 通信封装

- 所有 Remote 通信必须统一封装在 `NetMsg` 中使用。
- 客户端使用的 `BindableEvent` 必须统一封装在 `ClientMsg` 中使用。
- 服务端使用的 `BindableEvent` 必须统一封装在 `ServerMsg` 中使用。
- 业务代码中禁止直接引用或创建 `RemoteEvent` / `BindableEvent` 实例。
- 业务层只能通过 `NetMsg` / `ClientMsg` / `ServerMsg` 发送或接收消息。
- 请求类消息：发送使用 `FireRequest<名字>`，接收使用 `ConnectRequest<名字>`（如 `FireRequestSetBGMVolume` / `ConnectRequestSetBGMVolume`）。
- 通知类消息：发送使用 `FireNotify<名字>`，接收使用 `ConnectNotify<名字>`（如 `FireNotifyPlayerInfoInit` / `ConnectNotifyPlayerInfoInit`）。
