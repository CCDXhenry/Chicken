# 架构与配置

提取自成熟工程的架构与核心约束，结合 Chicken 实际业务适配。

## 调用链与模块职责

- 服务端主入口位于 `Scripts/ServerScriptService/RoastChickenServer/`。子系统与模块职责清晰划分（如动物/生产、餐厅经营、金币与升级等）。
- 客户端主入口位于 `Scripts/StarterPlayer/StarterPlayerScripts/RoastChickenClient.local.luau`。负责输入处理、本地 HUD 渲染、玩家属性监听与请求发起。
- 数据与状态管理：服务端作为业务状态的唯一权威来源；客户端仅做数据展示映射与本地预测。业务计算与逻辑校验在服务端完成，UI 通过数据层读状态、监听属性或消息刷新。
- 跨端通信统一通过 `RemoteEvent` / `BindableEvent` 封装，不在各个业务细节中随意裸调或硬编码通信实例。
- 新系统由主入口集中初始化，不以模块 `require` 的隐式副作用启动。

## 配置与类型

- 共享配置置于 `Scripts/ReplicatedStorage/`（如 `FarmEconomyConfig.luau`）。系统配置独立模块化维护，不把庞杂的状态机塞入单一纯数据表。
- 新增或维护配置时，在默认值处写中文注释，说明用途、单位、默认值意图和有效边界；未消费或预留字段如实标注。类型声明处不重复维护同一份说明。
- 标识符、字段、Tag、Attribute 及内部字符串标识统一使用英文；中文用于注释、开发日志及翻译表。面向玩家的源文案统一规范维护。
- 运行时资源 ID 集中在正式配置中；美术上传记录、文档索引和参考映射不作为 require 的运行时依赖。
- 大数展示优先考虑通用格式化机制，避免数字溢出或显示破框。

## 存档与服务兼容

- 存档更新时注意结构兼容性：检查默认值、读写逻辑、客户端同步类型及版本迁移工具。需要迁移时维护版本迁移，不只改类型声明。
- 持久化 Map 统一使用 string key；数值 ID 用 tostring 转换，或持久化为 List，运行期再建 number-key Map。
- 不把未实际生效的外部服务权限写成“已接入且验证成功”。
